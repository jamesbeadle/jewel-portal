What every view is actually made of

An anatomy of all 89 views, read out of the razor source. The point is the gap it exposes: the app has 344 components defined, but the furniture that appears on nearly every page — the title row, the chip tabs, the alert box, the status pill, the records table — is hand-rolled Tailwind, page by page. Those are the components a design system has to own first.

What the sweep found

Five duplications worth fixing before anything else

Every batch of pages reported the same handful independently, which is the strongest signal you can get from a survey like this. Counts are grep-verified across jpms/Pages.

The auth preamble

52 of 89 pages hand-roll the same three-branch !isLoaded → LoadGate / !IsApproved → RequestAccessView opener. ApprovedSessionGate already does exactly this and only 24 pages use it. Roughly 15 lines deleted per file, no design decisions needed.

The page header

68 of 89 pages build their own eyebrow / title / subtitle / right-hand action cluster. No PageHeader component exists at all. It is the most-seen element in the product and the least owned.

The status pill

Components/StatusPill.razor exists and is used by zero pages — every one of the 24 pages showing status hand-rolls its own rounded-full span, so the same status reads differently from register to register.

The alert banner

Reported by all eight batches, often two or three per page: a rounded-lg border px-3 py-2 message box for errors, warnings and confirmations, with the Tailwind classes drifting slightly every time. Nothing owns it.

The records table

29 pages hand-roll a <table> with their own header row, select-all checkbox, sort affordance and row menu. SortableColumnHeader exists and no page uses it; seven domain tables have been extracted, the rest never were.

The healthy one

LoadGate is on 70 pages and behaves consistently — the loading convention in CLAUDE.md worked. It is the proof that a written rule plus one component is enough to get adoption here.

The proposal

A component spine, in six tiers

Names taken from what the views already do, not invented. Have means it exists and is used; idle means it exists and pages ignore it; build means nothing owns the pattern yet. The last column is how many of the 89 views need it, which is the order to build in.
